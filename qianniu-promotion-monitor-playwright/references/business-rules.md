# 巡检业务规则

## 范围与阈值

每店串行读取阿里妈妈全站推（`all-site`）和关键词推广（`keyword`）。ROI、花费为空时按 0 参与低 ROI 提醒、暂停候选和写前复核的阈值判断。暂停、删除、查询不到和状态未知的记录不能被当作活动候选。

| 判定 | 默认条件 | 边界 |
| --- | --- | --- |
| 低 ROI 提醒 | `ROI < notifyRoiBelow`，默认 2 | ROI 等于 2 不提醒 |
| 待暂停 | `花费 > closeChargeAbove` 且 `ROI < closeRoiBelow`，默认 30 与 1.5 | 花费等于 30 或 ROI 等于 1.5 不暂停 |
| 已暂停 | 本轮候选在后续定向核验中明确处于停用状态 | 请求成功、列表缺失或指标变低均不能单独证明 |

空值与缺失值按 0，非空数值保持原始精度。报告中的 ROI 和花费仅显示两位小数，不先四舍五入再判阈值。ROI 空且花费大于 30 时，按 ROI 为 0 暂停；花费空时按 0，不满足暂停条件；两者都空时不暂停。空 ROI 同样满足默认的 `ROI < 2`，可进入低 ROI 列表。

即使某类推广全部计划的 ROI、花费均为空，也按零值正常完成扫描，不报指标缺失、不统计缺失数量，不因此将该店标为 `needs_review` 或阻止其他候选暂停。非空非法指标、登录失效、身份不符、接口失败和响应结构异常仍须保留真实错误，不将失败请求或无法解析的数据当作零花费。

不通过名称模糊匹配计划；目标键同时包含店铺 id、推广类型和计划 ID。分页必须完整；达到页数上限或返回结构异常不能宣称整店扫描完成。

## 日期与报表口径

每轮指定一个 `YYYY-MM-DD` 日期，缺省为 Asia/Shanghai 当天；本轮日期写入扫描输入与审计，恢复不改日期。首次读取显式覆盖查询起止日期，同时保留页面有效来源、归因等查询上下文。扫描记录的 `reportContext` 随候选保存。

初次暂停复用该候选的扫描上下文，不能读取持久页面上可能残留的旧日期。恢复定向查询仍使用本轮日期；允许的恢复写入使用最近一次核验获得的完整上下文。页面运行时未能提供有效口径时停止该目标，不自行补猜归因字段。

## 身份与执行

用户的显示别名与阿里妈妈返回身份分别保存。`store` 用于报告展示，显式填写的 `expected_alimama_shop` 始终作为严格的店铺名约束，同时提供 `login_username` 时增加完整账号精确核验。即使账号匹配也不能放宽显式店铺名约束。

未提供 `expected_alimama_shop`、但提供了已确认的 `login_username` 时，在业务查询前先精确核验页面运行时完整昵称，成功后绑定该页面实际返回的 `shopName/nickName`；`store` 可保留工作台显示别名。不按主账号前缀匹配，不把普通备注当完整账号，也不推猜账号与店铺的对应关系。真实店铺名与完整账号都未提供时，沿用 `store` 与实际店铺名精确比较。

实际 `shopName/nickName` 在同轮全站推和关键词推广之间保持一致，并约束后续暂停与恢复；身份变化时停止。该绑定持久化为 `scan_identity`，即使扫描为零条也保存，不靠候选记录间接保存身份。恢复不能用新观察值覆盖原绑定来放宽检查。

执行时逐计划重新读取身份、状态和指标。最新指标已不符合任一阈值时跳过写入并保留证据；指标有所改善但仍符合全部条件时仍按规则处理。明确写前拒绝为 `not-written`，写后结果未知为 `uncertain`，二者不能混称“已提交暂停”。

执行后按本轮候选的计划 ID 逐项核验，不能重扫全店来推断结果。身份不符、查询失败、筛选未生效、找不到目标都记待核验。登录失效是该店铺环境的终止条件，不继续扫描重试、暂停或重复回查；人工重新登录后恢复。

登记目录中的 `.promotion-monitor.lock` 使整轮批次互斥，不改工作台调度。单店结果先落盘并记为 `closing`，再保存 taobao/tmall/alimama 会话到原 Profile，正常关闭浏览器并确认进程退出，随后才确认收尾并进入下一店。关闭阶段中断的店铺恢复时不能按成功跳过。会话保存或关闭失败时保留现场并停止批次，不强杀或继续累积已打开的店铺；单纯登录或指标异常在收尾成功后允许继续。`--keep-browser` 明确改为只断开保留窗口；新批次的 `close_after_shop` 冻结，旧批次无字段继续保留浏览器，恢复不能更改。

## 恢复与通知语义

恢复默认只读。允许恢复写入须同时具备本轮执行授权、明确目标清单、逐目标旧操作已结束证据，以及最新核验仍活动且仍符合条件。旧操作结束证明必须对应具体计划；关闭一个页面不能证明整店所有请求都结束。超时本身也不是结束证据。恢复预算持久化，重新启动命令不重置预算。

待暂停清单保存首次决策，核验和执行结果追加到该目标，不抹掉最初候选。“已暂停”只从最新核验确认停用的候选中产生；一个目标可同时出现在待暂停与已暂停两阶段列表。确认仍活动标注“仍在推广”，结果不明标注“待核验”。

`report` 仅本地报告，即使已设置 Webhook 也不通知。`dry-run` 需要提醒授权，`execute` 需要暂停授权；只有暂停授权时增加 `--no-notify`，有发送汇总授权才启用通知。新批次使用 `after_batch`：每次正常批次处理结束发送一次汇总，即使仍有 `needs_review` 或因关闭失败等原因 `stopped`，也列出已取得结果、待核验与未执行范围。Ctrl+C / 取消会保存 `stopped`，但取消清理时不发送，可之后恢复或另行 `--finalize`。按企业微信长度拆条仍视为同次汇总；发送快照冻结实际文本和当时的检查点引用，不能混用之后恢复的数据。

新批次已发汇总但业务未完成时可 `--resume` 只读恢复，旧发送记录保存在 `notification_history`，恢复结束再发送新的汇总；已 `complete` 时恢复跳过，不重发。`sending` / `delivery_unknown` 阻止重发及恢复。旧批次缺少通知策略时继续按原完成后发送规则处理，不自动迁移。通知关闭后不再启用；暂停结果未知时仍不能自动重放写请求。

`pending` 且部分消息已送达时禁止恢复改写，可 `--finalize` 续发冻结原文中的剩余消息；`pending` 尚未送达任何条目时，允许恢复后重建未发快照。不能重发已确认送达的条目，也不能把发送结果未知当作未发。

通知先按店铺分组列低 ROI 结果，最后集中列“待暂停 / 已暂停”。按空值归零后的指标说明候选结果，不展示缺失指标提醒、缺失计数或“推广未暂停”计数，不将技术错误、trace 或凭据放进企业微信。

## 迁移来源与维护

业务规则与页面运行时适配参考上游 `sycamorestr/qianniu-promotion-monitor` 的提交 `20245634b75ca2597668fb35175d0a31482165a5`。新入口改为 Python + Playwright CDP，浏览器启动、数据目录锁与多店登记方式参考开票技能。原 OpenCLI 配置中的 profile 标识不是 CDP 浏览器配置，不应直接复制作为环境身份。

平台页面或接口变更时先复现授权范围内的只读查询，核对实际请求与响应，再维护 `adapters/`，不凭旧文档猜写接口。离线测试用于验证本地规则、状态机和模拟响应；线上账号、页面运行时、实际通知及暂停结果需分别验证，并记录店铺数量与操作范围。

2026-09-29，采用空值归零规则的最新真实 `execute` 巡检已完成 9 店、385 条计划，全部店铺正常完成，登录态保存与浏览器关闭均成功。企微汇总 5 条均获接口成功响应，整轮耗时 3 分 34 秒。本轮无符合条件的暂停候选，实际暂停 0 条，因此真实暂停接口尚未在线上触发。当前版本通过 98 项 Python 与 17 项适配器离线测试；隔夜登录未验收。旧审计和已发送消息保留原快照，不按新规则改写历史记录。
