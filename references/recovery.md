# Agent 异常恢复

当前执行 runner 的 agent 就是恢复责任人，不需另建定时任务或调用额外模型 API。runner 出错后先保存审计并返回 `awaiting-agent`；agent 读取后继续工作，完成恢复再发企微。

## 检查和核验

1. 读取该 run 的审计与错误阶段；只提取脱敏 trace 的错误码、阶段、计划身份、写入回执。不要输出 Cookie、CSRF、Webhook、请求头或完整网络日志。
2. 有 `pendingRuns` 时先恢复这些历史 run。出现 `runner.lock` 时核对记录 PID；进程仍在运行就等待。确认 runner 已退出后，agent 可删除这个明确路径的陈旧锁文件，再恢复审计；不要凭锁过期或 runner 退出就假定浏览器中的旧操作结束。
3. 使用 `node runner.mjs --recover RUN_ID`。它不写入、不通知：已筛出候选的店仅按候选 ID 定向核验，不重扫整店，也不打开无关推广类型；首次扫描失败的店才补扫以确定候选。目标必须返回明确活动或暂停状态，查不到不能当作已暂停。历史已发送的 run 可以只读回查，但不会重发通知、重放写入或创建新的阻塞记录。未完成 partial 也通过此入口恢复，恢复后保留为 recovered-checkpoint 审计。
4. 根据本轮 trace 诊断超时、页面就绪、登录或身份问题。识别到登录页、未登录或会话过期后，停止该 profile 的扫描重试、暂停写入和重复回查，等待重新登录；其他 profile 仍可继续。普通错误只重试失败范围；只读恢复每店、每推广类型最多两次，某一类型失败不覆盖另一类型的明确结果。默认命令级超时为 180 秒、runner 外层为 420 秒；若临时调整，`OPENCLI_TIMEOUT_MS` 必须至少为两倍命令级秒数再加 60 秒，为失败证据采集和进程收尾留出空间。不要永久盲目调大超时。错误会脱敏保存在审计，完整 trace 留在本机。

## 允许恢复写入的条件

- 原轮为明确授权的 execute，目标属于该轮待暂停清单；恢复失败扫描店时可加入该店新鲜扫描产生的合规候选。
- agent 已确认该 profile 的旧页面操作结束。OpenCLI 超时只拒绝等待，不取消页面操作；`pending=0`、没有 lease、进程退出或单纯等了一段时间均不足以单独证明结束。可用完整命令完成证据，或确认旧操作所在页面/会话已关闭的证据。无法确认时保持只读。
- 最新目标查询身份匹配、同一计划明确仍活动且指标完整并仍符合阈值。恢复命令会再定向读取一次，并由暂停适配器做紧邻写入的身份、名称、类型、活动状态及指标检查。

满足条件后：

```text
node runner.mjs --recover RUN_ID --retry-pauses --settled-profiles PROFILE_A,PROFILE_B
```

`--settled-profiles` 是 agent 对已检查 profile 的明确声明，不能为了通过门禁随意填写。每计划恢复写入预算为一次，在调用前落盘；即使进程中断也不会重新获得重试机会。同一计划再次写入不确定就停止该计划后续写入，继续只读回查；同店其他计划独立处理。暂停命令使用 persistent 会话配合 OpenCLI 写入锁，页面可能保留；锁只辅助防并发，不证明之前的写入已经结束。

已发通知的历史轮次不会再次执行暂停。若它仍持有 pending 阻塞记录，agent 确认旧操作结束后可用 `--recover RUN_ID --settled-profiles PROFILE` 只读核验：明确仍活动时释放该历史轮次的阻塞，让后续已授权轮次按新鲜清单处理；未知状态继续保留。此操作不发消息、不写店铺。

## 最终通知

通常最多两轮 agent 恢复。仍有身份/登录障碍、旧操作无法确认结束、指标不完整或重试已耗尽时，保留待核验记录并说明当前限制，不无限重试。

```text
node runner.mjs --finalize RUN_ID
```

该入口不访问浏览器，只按最新审计发送。最新回查失败或仍活动时，旧的成功回执不能让该项出现在“已暂停”。“待暂停”保留原始完整执行清单；“已暂停”只包含最后核验确认停用的子集。普通巡检分包在前，暂停操作汇总分包在最后。

通知 `sent` 时不重发；`sending`/`failed` 可能已送达部分分包，需要核对投递结果，不重跑业务流程。本轮原始异常继续保留供维护，是否恢复成功以最新核验为准。
