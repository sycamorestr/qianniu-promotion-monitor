# Agent 异常恢复

当前执行 runner 的 agent 就是恢复责任人，不需另建定时任务或调用额外模型 API。runner 出错后先保存审计并返回 `awaiting-agent`；agent 读取后继续工作，完成恢复再发企微。

## 检查和核验

1. 读取该 run 的审计与错误阶段；只提取脱敏 trace 的错误码、阶段、计划身份、写入回执。不要输出 Cookie、CSRF、Webhook、请求头或完整网络日志。
2. 每轮执行独立，历史 pending 只保留审计，不需要在新 run 前恢复，也不阻断新 run 的暂停。出现 `runner.lock` 时核对记录 PID；进程仍在运行就等待。确认 runner 已退出后，agent 可删除这个明确路径的陈旧锁文件，再恢复审计；不要凭锁过期或 runner 退出就假定浏览器中的旧操作结束。
3. 使用 `node runner.mjs --recover RUN_ID`。它不写入、不通知：已筛出候选的店仅按候选 ID 定向核验，不重扫整店，也不打开无关推广类型；首次扫描失败的店才补扫以确定候选。目标必须返回明确活动或暂停状态，查不到不能当作已暂停。历史已发送的 run 可以只读回查，但不会重发通知、重放写入或创建新的阻塞记录。未完成 partial 也通过此入口恢复，恢复后保留为 recovered-checkpoint 审计。
4. 根据本轮 trace 诊断超时、页面就绪、登录或身份问题。识别到登录页、未登录或会话过期后，停止该 profile 的扫描重试、暂停写入和重复回查，等待重新登录；其他 profile 仍可继续。普通错误只重试失败范围；只读恢复每店、每推广类型最多两次，某一类型失败不覆盖另一类型的明确结果。默认命令级超时为 180 秒、runner 外层为 420 秒；若临时调整，`OPENCLI_TIMEOUT_MS` 必须至少为两倍命令级秒数再加 60 秒，为失败证据采集和进程收尾留出空间。不要永久盲目调大超时。错误会脱敏保存在审计，完整 trace 留在本机。

## 诊断暂停失败

先运行 `node scripts/diagnose.mjs --trace-dir <该命令的 trace 目录>`。摘要只显示固定错误类别、阶段、查询/写请求计数及报表日期，不输出 URL 参数、请求头、凭据或响应正文。只读诊断不会改变审计、暂停计划或发送通知。

- `not-written`/明确写前拒绝：本次未提交暂停，不推测为服务器拒绝或未知写入。仍读取目标最新状态；完整指标已不再符合阈值时不执行，仅有改善但仍符合阈值的按原规则处理。
- `uncertain`/`Runtime.evaluate` 超时：无法仅凭退出码判断是否提交。OpenCLI 1.8.7 的 trace 默认只保留最近 120 秒，长时间超时会丢掉开头事件；没有 command start 或网络记录不能证明未写入，也不能证明旧操作结束。
- 诊断为 `pause-outcome-uncertain` 时已进入写后错误路径，即使错误内嵌预检文字，也不能归为未写入。`durationSource=observed-events-only` 只是残存事件的跨度，不是整条命令耗时；`writeRequests=0` 仍不能证明未提交。
- 同计划扫描与写前指标明显不同：检查 `reportContext` 的日期和归因口径，再判断是否确实改善。暂停必须使用本轮扫描口径，恢复暂停使用最新核验口径，不采用旧后台页的日期。
- 页面等待超时：扫描/暂停的等待和就绪轮询在 Node 中执行。暂停保留 persistent 写锁，但使用新建并绑定的专用页面；不通过延长网页内 `setTimeout`、重放整段脚本或去掉阈值解决。
- 清理结果：成功回执的 `cleanup.pageClosed=true` 或对应 `pauseAttempts` 记录的 `pageClosed=true` 是该次专用页面已关闭的证据；按记录中的店铺、推广类型和计划 ID 匹配目标，`false` 或缺失不作此结论。关闭失败不覆盖原预检错误或已核验结果。关闭页面只能证明该页面不再继续执行，仍需定向核验服务器状态。

## 允许恢复写入的条件

- 原轮为明确授权的 execute，目标属于该轮待暂停清单；恢复失败扫描店时可加入该店新鲜扫描产生的合规候选。
- agent 已确认该目标计划的旧页面操作结束。OpenCLI 超时只拒绝等待，不取消页面操作；`pending=0`、没有 lease、进程退出或单纯等了一段时间均不足以单独证明结束。可用完整命令完成证据，或确认该次旧操作所在页面/会话已关闭的证据。单条计划的 `pageClosed=true` 只证明该次页面结束，不代表同店其他操作结束；无法确认的目标保持只读。
- 最新目标查询身份匹配、同一计划明确仍活动且指标完整并仍符合阈值。恢复命令会再定向读取一次，并由暂停适配器做紧邻写入的身份、名称、类型、活动状态及指标检查。

满足条件后：

```powershell
node runner.mjs --recover RUN_ID --retry-pauses --settled-targets '[{"profile":"PROFILE_A","promotionType":"全站推","campaignId":"CAMPAIGN_ID"}]'
```

`--settled-targets` 是非空 JSON 数组，每项只包含 `profile`、`promotionType`、`campaignId` 三个字符串，推广类型为 `全站推` 或 `关键词推广`；完整身份必须对应当前 run 已记录的候选。重复项、未知目标和字段错误会在浏览器操作及审计写入前拒绝。首次扫描失败尚无候选时，先只读恢复补齐候选，再根据目标证据声明结束。

兼容入口 `--settled-profiles PROFILE_A,PROFILE_B` 是对这些店铺全部相关旧操作均已结束的声明；只有逐一确认后才可使用。与 `--settled-targets` 同时使用时按两者的并集处理，不能为了通过门禁扩大范围。声明只允许核验后的受控重试，不保证目标仍符合规则。

每计划恢复写入预算为一次，在调用前落盘；即使进程中断也不会重新获得重试机会。同一计划再次写入不确定就停止该计划后续写入，继续只读回查；同店其他已分别确认旧操作结束的计划独立处理，登录失效仍停止该店。暂停命令使用 persistent 会话配合 OpenCLI 写入锁，并关闭该次创建的专用页面；清理失败或进程中断时页面可能保留。锁只辅助防并发，不证明之前的写入已经结束。

已发通知的历史轮次不会再次执行暂停；需要审计补充时可用 `--recover RUN_ID --settled-targets JSON` 做只读核验和逐目标结束确认，不加 `--retry-pauses`。历史项无论明确或未知，都不影响后续已授权新轮次按新鲜清单执行。此操作不发消息、不写店铺。

## 最终通知

agent 通常每个 run 累计最多恢复两轮，以审计中的 `recovery.rounds` 和 `retryCounts` 为准；脚本记录累计轮数并强制每计划最多一次恢复写入，两轮停止点由 agent 执行。重新调用命令不会重置轮数或每计划预算。仍有身份/登录障碍、旧操作无法确认结束、指标不完整或重试已耗尽时，保留待核验记录并说明当前限制，不无限重试。

```text
node runner.mjs --finalize RUN_ID
```

该入口不访问浏览器，只按最新审计发送。最新回查失败或仍活动时，旧的成功回执不能让该项出现在“已暂停”。“待暂停”保留原始完整执行清单；“已暂停”只包含最后核验确认停用的子集。普通巡检分包在前，暂停操作汇总分包在最后。

通知 `sent` 时不重发；`sending`/`failed` 可能已送达部分分包，需要核对投递结果，不重跑业务流程。本轮原始异常继续保留供维护，是否恢复成功以最新核验为准。
